# AI Ads

An agentic app that takes an ecommerce marketer from a store URL to 9:16 portrait image ads they would actually run. The example store is https://www.loopycases.com.

## Product loop

URL → **Research** (brand + products) → **Generate** (image ads) → **Manage** (review, iterate, approve) → feedback back into Generate. The agent does the work; the user steers.

- **Onboard:** research the brand (logo, colors, voice, value prop, audience) and pull real product images and details from the store. Decide deliberately what is scraped, what is inferred, and what is asked of the user.
- **Generate:** full-screen 9:16 portrait ads built on the store's **real product photos**, never an invented product, with the headline and CTA rendered inside the image.
- **Manage:** brand kit, campaigns, ads, variants, assets and status persist in Supabase. The user can give feedback, edit, regenerate and approve.
- **Human in the loop:** at least one point where the agent pauses for user input, and one where user feedback changes the next generation.

Working software that feels good beats breadth. Tool failures must degrade gracefully, never dead-end.

## Stack (fixed by the brief — do not swap layers)

- Next.js 16 App Router, React 19, Tailwind 4, TypeScript
- Vercel AI SDK + AI Elements for the agent and chat UI (streaming, tool calls, generative UI); **Vercel Workflow** (`workflow`, `@ai-sdk/workflow` `WorkflowAgent`) runs the agent durably
- Supabase: Postgres, Storage, optional Auth (a single demo user is fine)
- fal.ai for image generation. fal URLs are not durable: **always copy outputs into Supabase Storage** and store our URL, never fal's.
- Firecrawl or a web search API for research
- LLM via Vercel AI Gateway
- Hosted on Vercel, project `jiu-jiu-s-team/ai-ads`, connected to GitHub `jooj99/ai-ads`. Pushes to `main` deploy to production at https://ai-ads-dusky.vercel.app; PRs get preview deploys.

## Check current docs, not memory

Next.js 16, the AI SDK and AI Elements change faster than model training data. Before writing framework code, read the version-matched docs instead of relying on recall:

- Next.js: `node_modules/next/dist/docs/` (matches the installed version). Heed deprecation notices.
- `cacheComponents` and `partialPrefetching` are enabled in `next.config.ts`, so caching follows the Cache Components model (`"use cache"`, `cacheLife`, `cacheTag`), not older `fetch`/`unstable_cache` patterns.
- AI SDK, AI Elements, Supabase and fal: check their current docs or the installed packages' types before using an API.

## Auth (one demo user)

- **Supabase Auth, email + password, one user.** `@supabase/ssr` keeps the session in cookies. The auth client (`lib/supabase/auth.ts`) uses the publishable key, so it can sign in but still can't read tables; data stays on the secret-key client. Auth only decides who may use the app, so tables have no `user_id` and RLS stays policy-free.
- `proxy.ts` runs on every page and API request: it refreshes the session (`getClaims()` verifies the JWT) and sends signed-out visitors to `/login?next=<path>` (pages) or a 401 (API). It skips Next's assets, images in `public/`, and `/.well-known/workflow/*` (the Workflow runtime calls those server-to-server, with its own queue key). Without the public Supabase env vars it fails closed.
- Checks don't rely on the proxy alone: every route handler starts with `unauthorized()`, every server action and data-loading page with `requireUser()`.
- `/login` (`app/login/`): `signIn` / `signOut` server actions; `next` only accepts same-site paths. Sign out is in the sidebar's account menu.
- The demo user is created with `npm run demo-user` (`scripts/create-demo-user.mjs`, admin API, already confirmed; rerun to reset the password) from `DEMO_USER_EMAIL` / `DEMO_USER_PASSWORD` in `.env.local`. There's no sign-up page; public sign-ups should also be off in the Supabase dashboard (Authentication → Sign In / Providers → "Allow new users to sign up"), since the publishable key could otherwise register accounts through the API.

## Campaigns and brand research

- Home's **Start Campaign** (`app/actions.ts` server action) validates the URL, inserts a `campaigns` row, claims it (`claim_research` SQL function: one run at a time, a run quiet for 5 min counts as dead), starts the durable research run (`start(researchRun, [id])`), records it as the campaign's active run with its opening message (`openResearchThread`, `lib/agent/research-thread.ts`) and redirects to `/campaigns/[id]`. `POST /api/campaigns/[id]/research` starts a run the same way (from the empty-chat card's Start / Restart research, or the agent's full re-run) and returns the run id and opening message.
- Research runs **independent of any page**: it's a durable Vercel Workflow run (see the agent section), so leaving the page, function timeouts and restarts don't stop it, and the page reconnects to its stream. **Supabase Realtime** (`lib/realtime.ts`) still carries headline changes (status, name, logo, current step, and ads in progress) on `campaigns` for the live Campaigns grid, and a `finished` event on `campaign:<id>`. Broadcasts are sent with the secret key and received with the publishable key; tables stay locked behind RLS.
- Without `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (Vercel only syncs them to Production; locally they're in `.env.development.local`) pages fall back to polling.
- Supabase schema: `supabase/migrations/` (`campaigns`, `brand_kits` 1:1, `campaign_products`, `campaign_chats` 1:1, `campaign_headlines`, `campaign_ads` (versions via `parent_id`), `ad_comments`; private Storage buckets `brand-fonts` and `ads`). RLS is on with no policies; all access goes through `lib/supabase/server.ts` with the secret key, and `lib/campaigns.ts` is the only data layer. Apply migrations with `npx supabase@2 db push --db-url "$POSTGRES_URL_NON_POOLING"`.
- `campaign_products` holds the **whole** researched catalog, each row typed (`type_name`) with heroes flagged (`is_hero`); the Product selection filters All / Hero picks / each type.
- Editing: click the campaign title to rename; delete from the campaign page or list card; remove colors/fonts from the brand kit. All go through server actions in `app/campaigns/actions.ts`. Research only renames a campaign while its name is still the default (the domain).
- What the research steps do: Shopify detection (`/meta.json`) and the homepage read (Firecrawl full page incl. navbar and footer: `markdown` + `branding` + `links` + `rawHtml`); a quick Haiku call (`lib/research/offering.ts`) classifies the business as **goods or services**; the catalog follows from that (`lib/research/catalog.ts`): goods use Shopify `/products.json` or one product page per navbar category, services use the site's service pages and their own photos (never the Shopify retail shop). Then two `streamText` + `Output.object` calls (`lib/research/insights.ts`) write value prop, audience and voice, and group the **whole** catalog into at most 10 kinds of product/service (styles and collections are not types) with 1–2 hero picks each. Picks without photos get their pages read afterwards (plain HTML first, to spare Firecrawl's ~15 req/min free limit).
- **Research is built from steps** (`lib/research/steps.ts`): `detectPlatform`, `readSite`, `classifyOffering` / `setOffering`, `listSiteLinks`, `findOfferingPages`, `loadCatalog`, `addProductFromLink`, `removeProducts`, `writeBrandInsights`, `groupCatalog` / `setProductTypes`, `findPhotos`, plus the read-only `getCatalog` and `researchStatus`. Each reads what earlier steps stored, does one job, saves, and returns a one-line summary; a missing input throws `StepPrerequisiteError` naming the step to run first. The agent runs them itself as tools, following the research skill (usual order: platform ∥ homepage → offering → catalog → brand insights ∥ grouping → photos). The insights call is split in two (`streamBrandInsights`, `streamCatalogGrouping`, both taking optional `guidance`); the Haiku calls take `guidance` too. Each session saves only the kit columns it changed, so steps running in parallel don't overwrite each other.
- **Research state** (`lib/research/state.ts`, `ResearchSession`): `research_snapshots` keeps what steps read (page reads by URL, the Shopify detection, the link picks). Products merge by `source_id` (unique per campaign) and keep `listed_type`, `tags` and `origin`; a "replace" re-run only drops research-added items, and a full re-read is the truth about photos. Fields the user or agent edit are listed in `brand_kits.edited` (via `updateKit`'s `fields`) and research never overwrites them unless the session is opened with `force`. After page-based loads the shared-photo rule (`sharedPhotoCleanup`) runs over the whole merged catalog, photos are applied per item id, and photo searches skip pages that describe several items (the homepage, a pricing page); videos and YouTube thumbnails are never photos. Merges match items by id or by page URL (host without www, path), so the same product found as a Shopify id and as a page isn't duplicated; items titled like error pages ("404 Not Found") are dropped. `loadCatalog` with `mode: "add"` requested in chat runs as the agent, so those items are marked `origin = agent` and survive research re-runs.
- When Firecrawl's `branding` leaves gaps (no real logo, under two colors, missing or internal font names), `lib/research/html-signals.ts` reads the rendered HTML plus up to four stylesheets: logos from structured data, `<img>`, CSS `mask`/`background` images (scored by home link, aria-label and selector so header icons lose) and inline SVG; colors from CSS design tokens; readable font names from `@font-face` files. If there's still no logo, `probeLogoPaths` checks `/logo.svg`, `/assets/logo.png` and similar.
- **Brand font files:** research always reads the site's stylesheets (`fetchStylesheets`, keeping each sheet's URL so relative `url()`s resolve; up to `MAX_FONT_STYLESHEETS` = 40 plus one level of `@import`, font stylesheets first, while colors/logos still use the first 4). Stylesheets and font files are fetched like a browser would (`assetHeaders`: browser UA, `Accept`, `Referer` = the declaring stylesheet then the page, `Sec-Fetch-*`), because some CDNs refuse bare requests (apple.com 404s its font CSS and files without them); a face's other formats (woff, ttf) are tried if the first fails and `fontFilesFor` attaches each brand font's own `@font-face` files (regular ≈400 and bold ≈700, upright, WOFF2 first, the subset whose `unicode-range` covers "A"; names matched loosely and through internal aliases). After the run, `storeFontFiles` (`lib/research/font-store.ts`) copies them into the private `brand-fonts` bucket (checked by magic bytes, ≤2 MB, named by content hash) and the kit stores `/api/campaigns/<id>/fonts/<file>`, which streams them back same-origin with immutable caching. The font preview loads those with the FontFace API, then tries Google Fonts, then says it's a fallback. Deleting a campaign deletes its font files. Licensed fonts stay private to the campaign.
- Images: don't use Firecrawl's `images` format. It splits srcsets on commas inside image-CDN URLs (`static.nike.com/a/images/c_limit,w_318,…`), producing dead fragments. Request `rawHtml` and use `imagesFromHtml` (srcset-aware, reads `<picture><source>`, drops fragments via `isImageFragment`). A photo shared by two or more items, the homepage's share image and the logo are never an item's photo and are dropped (`withoutSiteChrome`, `notItemPhotos`, `pickPhotoExclusions`); self-described banners rank last (`DECORATION`). Items with no photo of their own (plans, integrations) show a typographic tile instead of a borrowed picture.
- Scraped facts (logo, colors, fonts, products, images) never pass through the model; it only returns product ids, which are matched back to the real catalog.
- Needs `FIRECRAWL_API_KEY` and AI Gateway access (OIDC via `vercel env pull`, or `AI_GATEWAY_API_KEY`). Without them each step degrades and says so instead of failing.
- Model: `anthropic/claude-sonnet-5.5` by default (needs paid Gateway credits); override with `RESEARCH_MODEL`. The local OIDC token expires after ~12h; rerun `vercel env pull .env.local` if the Gateway starts rejecting requests.

## Campaign workspace and agent chat

- `/campaigns/[id]` (`components/campaigns/campaign-workspace.tsx`): the panel (ads, brand kit, products) on the left and the agent chat on the right (`campaign-chat.tsx`; phones stack them, chat first), the Brand kit / Products / Ads tab buttons in the header (the `Tabs` root wraps the page; their content fills the right panel), and Delete in the ⋯ menu. **The ads are the main view:** the page opens on Ads once there are any and switches to it when the agent starts making or editing one. The chat input starts as one line and grows with the message.
- The research run appears in the thread as the agent's first turn (`research-progress.tsx`), still driven by the Realtime broadcasts above; it is not an LLM message.
- **The agent is durable** (`workflows/agent.ts`): `researchRun(campaignId)` (Start Campaign / Research again: the agent follows the research skill, then proposes headlines) and `agentTurn(campaignId, messages)` (one chat turn) are Vercel Workflow runs of a `WorkflowAgent`. Its instructions are built in a step (`loadAgentSetup`); every server tool call is its own retried step (`executeServerTool` → `lib/agent/server-tools.ts`, which also keeps a research run's heartbeat and the grid's step label fresh); the reply is rebuilt from the run's stream and saved by `saveRunThread` (seeded with the last assistant message when a submitted card continues it; skipped if a newer run took over). `campaigns.agent_run_id` is the active run. Routes: `POST /api/campaigns/[id]/chat` validates, saves the thread and starts `agentTurn` (header `x-workflow-run-id`); `GET …/chat/[runId]/stream` replays and follows a run (`[runId]` = the campaign id means its active run); `DELETE …/chat/[runId]` interrupts via the run's cancel hook (soft: the reply so far is saved), with `run.cancel()` as a backstop. The client uses `WorkflowChatTransport` and follows a run it isn't streaming with its own effect (`followRun` in `campaign-workspace.tsx`), not `useChat`'s `resume` option. With Cache Components, Next keeps the page's state when you navigate away but runs effect clean-ups; `useChat`'s clean-up stops the stream, and a resume replays the whole run as a new message. So the page keeps the messages from before each run (`runBase`: the messages it sent, or what showed when it began following), restores them before replaying, and never replays a run that ended or was stopped here (`endedRuns`). The effect also re-runs when the status settles, since a page coming back first renders its old "streaming" status. Without this, every return added another copy of each tool call. The chat route also drops repeated tool call ids (`withoutInterruptedParts`). `instrumentation.ts` starts the Workflow world so dev-server restarts resume runs. Steps re-run from the start after a crash, so they must stay idempotent (upserts by id).
- Brand kit panel: colors and fonts share a row; audience is tags (remove ✕ revealed on hover, add your own), saved with the same server action as color/font removals. Research still writes an audience description, but only the agent sees it. Hovering a font previews it (see brand font files below). Sections the user or agent edited show an **Edited** badge (from `brand_kits.edited`, plus panel edits optimistically); a hand-set grouping shows "grouping edited"; products the agent or user added show "Added by agent" / "Added by you". A chat with no messages yet (campaigns researched before research became the agent's run, or dead runs) shows `ChatStart` with the next action: start or restart research, or "Get headline ideas".
- **Human in the loop: products → ideas → ads.** Two pause tools, both with no `execute` (`PAUSE_TOOLS` in `lib/agent/tools.ts`), end the run with a question waiting; the page's answer becomes the tool output (`addToolOutput`, resumed by `sendAutomaticallyWhen`) and starts the next `agentTurn`.
  - **`chooseProducts`:** the research run ends with a short summary and this question (research skill, step 7), and so does any request for new ads that doesn't name products.
    - **Select mode:** the page switches to the Products tab in select mode (`ProductPicks`' `select` prop in `components/research/brand-kit-view.tsx`). A dark bar shows the question and the picks with Use / Cancel, and tiles become toggles with a check mark. The workspace opens it once per question (`seenAsk`), and the chat's "Pick in Products" button reopens it.
    - **Answering:** the output is `{ productIds, titles }`. Answering in chat instead closes the question as empty, and the agent matches what was written (`getCatalog`, `addProductFromLink`).
  - **Search:** the Products tab always has a search box (every word must appear in title, type, tags or description), combined with the type chips.
  - **`proposeIdeas`:** with products chosen, the agent loads the **ad-ideas skill** (`lib/agent/skills/ad-ideas/SKILL.md`). It's the creative playbook: grounded in audience, value prop and voice; varied formats (product in the wild, like a case dangling by its loop over a latte; quippy one-liner; problem → relief; POV/UGC; detail close-up; juxtaposition; seasonal; flat lay); shootable scenes; real products only, free staging; headlines that play off the image, no emojis. Ads never show emojis: the ideas tool and playbook forbid them, the image rules say none anywhere, and `withoutEmoji` (`lib/copy.ts`, also applied to idea cards, so saved and sent copy is clean too) strips any from the headline and CTA before the ad is made (keeping ©, ® and ™).
    - **The card:** the agent pitches 3–6 ideas, each with:
      - a title;
      - a `style`: `scene`, a photographic moment, or `minimal`, a clean graphic ad;
      - a `visual`: `product` (the product itself), `brand_graphic` (the brand's own graphics from the kit's brand visuals) or `none` (type only);
      - a 1–3 sentence `pitch`, the only text on the card;
      - a `direction`: the art direction for the image model, not shown;
      - headline, CTA and productIds.
      They render as `IdeaChoice` cards (`components/campaigns/idea-choice.tsx`) with Scene/Minimal and "Brand graphic" / "Type only" badges. Older ideas used `concept` / `scene` / `showsOff` / `showProduct`; those fields stay optional so old cards still load.
    - **The mix:** the playbook asks for at least 2 minimal ideas for services and software (at least one `brand_graphic`) and at least 1 for goods (a product hero or a bold claim). The agent's instructions list the kit's brand visuals by description; with none, it's told not to pitch `brand_graphic`.
    - **Generate:** ticking is local; **Generate N ads** saves each picked idea's headline + CTA to `campaign_headlines` (`proposal_id` = the card's call) and sends `{ picked }`. For an older card it sends a message ("Make these ideas from an earlier set: …"). Ideas already sent show "Made".
  - **Ads:** the agent calls `generateAd` once per picked idea, in parallel, with the idea's headline, CTA, productIds and `idea` (title, style, visual, pitch, direction).
  - **Old threads:** the old `proposeHeadlines` card still renders (`headline-choice.tsx`), but the model no longer gets it. The chat route keeps unanswered pause tools and closes them when the user moves on (`closeUnansweredChoices`).
- **Headlines are a list** in `campaign_headlines` (unique per campaign + headline + CTA, `source` agent/user, `proposal_id` = the idea card's or old headline card's tool call). Picked ideas add to it; the agent can change it in chat with `saveHeadline` / `removeHeadline`; the client re-reads it when a reply finishes. The agent's instructions list the saved headlines every turn, with the ones just picked listed apart. The Brand kit tab lists them below the kit (`HeadlinesCard`) with remove and write-your-own (saved directly).
- **Ideas in the brief:** an ad made from an idea gets a `creative_direction` (style, visual, the pitch, the art direction) at the top of its JSON brief, and the prompt opens with "Make the ad concept …". `adSystemPrompt(style, visual, hasLogo)` builds the standing rules:
  - **Minimal:** a plain or soft brand-color background, the logo small at the top, a very large bold headline, one visual element at most, a clean button and lots of space.
  - **Product visual:** product fidelity stays strict (design, color, print, every part where it is and as it attaches), and staging is free: any setting, person, pose, props, light, and any way of holding, wearing, dangling or using the product with its real parts.
  - **`brand_graphic`:** no product photos are sent, since on a software brand's pages they're often customer logos and headshots. Instead the kit's brand visuals go in (`brandGraphics`, `lib/ads/brand-assets.ts`), each named by its description, and the rule is to lift their 3D shapes, objects or illustrations as the ad's visual, without their text, screenshots or layout. With no visuals it falls back to `none`.
  - **`none`:** typographic.
  - **No usable logo file** (Ploy's bitmap-only favicon, Anthropic's inline SVG): the brand name is set as a plain wordmark, and the model is told never to make a logo out of another image. Before this rule, it turned a customer's "+" mark into a fake Ploy logo.
  - **The check:** when the product isn't shown, it only reports something presented as the brand's product or interface that isn't real; abstract graphics are fine. Product, brand-graphic and type-only ads don't need product photos to start.
  - **Studio:** the idea is saved as `campaign_ads.idea` (migration `20261120001500`) and shown under the ad's headline in the studio.
- **Brand visuals** (`lib/research/visuals.ts`, research step and tool `findBrandVisuals`, kit `visuals`, migration `20261120001600`): the brand's own graphics (3D shapes, a mascot, illustrations, patterns).
  - **Candidates:** the homepage share image, homepage images, the share images of hero pages (plain HTML reads), and the first catalog photos. Small thumbnail URLs are asked for at 1600px (`largeVersion`).
  - **Classification:** a vision model (`VISUALS_MODEL`, default the agent's model) classifies every candidate: brand graphic, product photo, lifestyle photo, person, another company's logo, own logo, screenshot, other. It sees each image with its context (where it was found, its file name) and is told that a mark named after another company, or one that looks like a standalone logo, is another company's logo even when it's stylized or 3D. Without that context it kept Clay's 3D arch logo as Ploy art. Only brand graphics are kept, strongest first (up to 6), each with a short description.
  - **Why:** the first Ploy ads only looked good by luck. Two of their "brand shapes" were customers' logos (Clay, Nursa) that research had taken from testimonial sections as the SEO agent's photos.
  - **Where it runs and shows:** it runs in research after grouping (research skill, step 5). Every research run also ends with `ensureBrandVisuals` (a workflow step before `finishResearchRun`), which runs it if the kit still has none. In testing the agent skipped the optional step. It doesn't block `researchStatus`, since some brands have none: Apple and Loopy Cases have none, Ploy has its glassy jelly shapes, Anthropic its engraving collages. The Brand kit tab shows them under colors and fonts ("Brand visuals").
  - **Tested:**
    - **Ploy:** a brand-graphic ad came out like the first Ploy ad: off-white, a big headline, Ploy's own jelly shapes, a plain "ploy" wordmark, a black pill button. It passed the check first time.
    - **Anthropic:** its engraved compass rose on cream, a serif headline, a plain "Anthropic" wordmark and a coral button. Same pipeline, a completely different look.
- **Generate (ads):** the agent's `generateAd` tool (`lib/agent/tools.ts`, run by `lib/ads/generate.ts`) makes one full-screen 9:16 ad per call with **Nano Banana Pro edit** on fal (`fal-ai/nano-banana-pro/edit`, `aspect_ratio: "9:16"`, 2K PNG, key `FALAI_KEY`). The agent calls it once per picked idea (above), with the idea's products (default: the first hero with a photo). `lib/ads/brief.ts` turns the kit into the model input: the products' real photos (only ones that load, checked first), the **real logo** and a **solid swatch image per brand color** (`lib/ads/brand-assets.ts`: swatches are 256px squares at `<campaign>/swatch-<HEX>.png`; both go to fal as 15-minute signed URLs), as `image_urls` (14 at most); standing rules (real products only, exact copy, safe zones) at the top of the prompt, since fal's documented input for this endpoint has no system field (stored separately in `campaign_ads.system_prompt` for review); and the ad's brief as **JSON** in `prompt` (headline, CTA, hero products by image number, each color as hex + role + the job it does from its role, e.g. Primary → the CTA button, + its swatch image, fonts with roles, voice traits and description, audience). The rules say to use swatch colors exactly (tested on Reconero: the CTA came out at the brand primary).
- **The logo is drawn by the image model** from the real logo image (`logoImage` in `lib/ads/brand-assets.ts`): fetched, rendered to PNG if it's an SVG (the largest PNG inside an `.ico`, since sites name favicons as logos; `rasterSource`), put on a solid background if it's transparent (white behind a dark mark, near-black behind a light one, with a margin; the prompts say that background isn't part of the logo), stored as `<campaign>/logo-<hash>.png` and sent with the brief. The check compares the drawn logo with the real one and the repairs fix it. Logos placed by code instead (keyed out, stamped in the calmest spot) were tried and reverted on the user's call: the columns it added (`base_path`, `logo`) were dropped again (migration `20261120001400`). The image is copied from fal into the private `ads` bucket and served signed-in only at `/api/campaigns/<id>/ads/<file>`; `campaign_ads` keeps each ad's status (generating/ready/failed), inputs and prompt. A retried workflow step finds its finished ad by `tool_call_id` instead of paying again. At most 6 ads per chat turn (`prepareStep`). The chat shows each call as a spinner, then a thumbnail. The model returns 1536×2752 PNGs.
- **Ads about a specific item:** the user can name one ("an ad for the gingerbread case") or paste a link to its page.
  - **Named items:** the agent's instructions list the whole catalog (title, type, price, hero, photo, id) when it has at most 80 items (`CATALOG_IN_PROMPT` in `lib/agent/prompt.ts`). For bigger catalogs it lists the heroes and searches the rest with `getCatalog`, whose `query` matches word by word, title counting double, best match first, or matches a page link.
  - **Links:** `addProductFromLink` (`lib/research/steps.ts`, runs as the agent, so the item shows "Added by agent" and survives research re-runs) reads that one page with `readProductPage` (`lib/research/catalog.ts`). It tries Shopify's `/products/<handle>.json` first (exact title, price, every photo, free), then Firecrawl's product read plus the rendered HTML, then plain HTML (JSON-LD Product, share image, `<img>`s). Photos are deduplicated by file name, with no thumbnails (size params ≤ 120), banners, review-widget shots, analytics beacons or third-party embeds. When the store lists product photos, other page photos count only from the same image host. On the brand's own site its logo and share image are never the photo. A link already in the catalog returns that item.
  - **Making the ad:** the agent passes the item's id to `generateAd`, using a saved headline that fits or writing one, saving it, then generating. `generateAd` refuses ids that aren't in the catalog instead of falling back to the first hero.
- **Failures and retries:** storing a finished image (already paid for) gets two more tries on a storage error before the ad fails. When an ad fails for a temporary reason (storage, timeout, image service busy), the agent says it's trying again and calls `generateAd` once more. The retry replaces the failed ad: `replaceFailedAd` (`lib/ads/render.ts`) deletes failed ads with the same headline and CTA that never got a version, and the new row takes their number (the numbering trigger keeps a given number). The studio hides a failed ad while its retry runs (not one from the running call itself), a running call's placeholder disappears as soon as an ad row from that call exists (`SavedAd.toolCallId`, so a finished ad and a "New" tile never show for the same call), and the chat labels the second call "Trying again: the ad for …" (`isRetry` in `campaign-chat.tsx`).
- **Ads that can't finish become failed** (`expireStaleAds`, `lib/ads/expire.ts`): a `generating` row whose agent run ended or no longer exists (`getRun(run_id).status`; a lookup error counts as alive) is marked failed ("The run making it stopped before it finished."), and so is any row still generating after 10 minutes (`AD_TIMEOUT_MS`, "It took over 10 minutes, so it was stopped."; its fal job is cancelled). It runs on reads, not a timer: the campaign page load, `listAdsAction` (which the workspace calls every 30s while any ad is generating) and `listCampaigns`. A run still alive after a timeout finds its row failed: `throwIfStopped` and `storeAdImage` throw `AdExpiredError` with the reason, so the tool reports it as a failure (and its result is thrown away). The studio shows an ad as being made only while its row is `generating` (the server is the truth; no client-side age check). The stream route returns 204 for a run that no longer exists, so the chat doesn't sit on "Thinking…".
- **Try again:** a failed ad (or failed version) shows its reason and a **Try again** button. For a new ad it sends "Try Ad N … again (ad <id>)"; the agent calls `generateAd` with `retryOf` = that id, which reuses the failed row's products and idea (`failedAd` in `generate.ts`) and replaces it with its number. The agent's instructions list failed ads with id, copy and reason. For a failed edit, the failed version is deleted and the edit asked for again: Apply on the open comments still on the edited version, else its instruction.
- **Live stages:** while an ad is being made, each phase writes what it's doing to `campaign_ads.stage` (migration `20261120001700`) and broadcasts it on `campaign:<id>` (`EVENTS.adStage`, `setAdStage` in `lib/ads/stage.ts`): "Drafting the image", "Checking the logo, products and text against the real ones", "Fixing the logo (round 1 of 3)" / "Fixing the product (the case in her hand) …", "Checking the fixes", "Saving the ad"; for edits "Applying 2 comments and your change", "Trying the edit again: a comment didn't take", "Removing leftover marks". The chat's running `generateAd`/`editAd` row (`adProgress` in `campaign-chat.tsx`, matched to its ad row by tool call id) shows which ad ("Making Ad 3: “…”", "Trying Ad 2 again", "Editing Ad 2 (v1)") with the stage under it; the studio shows it under "Making v3 of Ad 2…" and in a new ad's tile tooltip.
- **Finished ads show at once:** `broadcastAdActivity` also sends `EVENTS.ads` on `campaign:<id>` (an ad started, was stored, failed, was cancelled or expired), and `storeAdImage` sends it the moment an ad is ready, so the workspace re-reads its ads (`useCampaignChannel`) without waiting for the agent's whole reply. Next keeps the campaign page alive but unsubscribed while you're elsewhere, so the channel re-reads the ads every time it (re)subscribes; without Realtime the page polls every 5s while ads are generating (30s with it, as a safety net for expiry).
- **Local dev:** the local Workflow world keeps runs in `.next/workflow-data/world.db`. `npm run build` clears `.next`, which deletes in-flight runs of a running dev server (their ads then expire as above), so don't build while a generation is running.
- **Ad numbers:** every ad has a number per campaign (`campaign_ads.number`, "Ad 3"), assigned by a database trigger from `campaigns.ad_counter` (never reused, even after deletes); every version of an ad shares it, so an ad is all rows with one number. The agent's instructions list ads by number with each version's id, and it refers to them by number. `deleteAd` (agent tool and the studio's buttons, both via `lib/campaigns.ts`) deletes one version or the whole ad, images included.
- **Ads in progress on the Campaigns list:** each card's badge shows "Making 2 ads…", "Editing an ad…" or both while ads are generating (rows still `generating`, ignoring ones over 5 minutes old). `listCampaigns` counts them on load (`adActivity`, `lib/ads/activity.ts`), and `broadcastAdActivity` sends the campaign's counts on the campaigns channel when an ad row starts, when `generateAd`/`editAd` finish (ready, failed or stopped) and when a stop cancels a run's ads. A broadcast only beats the loaded count if it's newer (`CampaignSummary.adsAt`, the server time of the count), and the list re-reads when its subscription comes back: Next keeps the page alive but unsubscribed while you're on a campaign, so it misses the "done" broadcasts, and an old "Making 3 ads…" used to outlive the ads. The cards no longer show a product/service count or a date: the bottom right shows how many ads the campaign has ("3 ads": ads with a ready version, each counted once; `AdActivity.total`, sent with the same broadcasts). The workspace's Ads tab is just "Ads", with no count.
- **Ad check before showing** (`lib/ads/verify.ts`): every new ad's draft is checked by a vision model (`VERIFY_MODEL`, default the agent's model) against the real logo (shown on grey) and the product photos the brief sent (up to 6).
  - **What it flags:** a logo that isn't the real one, on the ad or printed on a product (`logo`: garbled, restyled, missing); a logo that looks pasted on (`logo_box`: in a box or patch of solid color that isn't part of the design, which the solid-background logo image can cause); a fake or altered product; or an invented screen/dashboard; or leftover editing marks (`artifact`: numbered circles, pins, drawn boxes, arrows, labels, stray digits, watermarks); or wrong copy (`copy`: the headline or CTA isn't exactly the given text, e.g. a repeated word). A copy repair gets an exact instruction built in code (what it reads now and what it must read) and no close-up crop, since a crop of the wrong text anchored the model to it. That fixed Anthropic's "Think it through. through. With Claude." in one edit. These get removed by the repair like any problem: tested on that Apple ad, one edit removed all six circles and left the rest unchanged.
  - **What each problem carries:** a fix, the tight box around the object (fractions), and what's in it ("the phone case in the woman's right hand"). Products are compared part by part (color, print, shape, and where each part sits and how it attaches, e.g. Loopy's finger loop lying flat down the back, not a strap hanging from the top) and in how they're held or used; each difference is its own problem. The generation rules ask for the same (parts stay where and as they attach, products used as the photos show). Problems get up to **3 repair rounds** (`MAX_REPAIRS`).
  - **Each round:** it chains one focused edit per problem (up to 4, `MAX_EDITS_PER_ROUND`), each on the previous edit's result, then checks once. The round is kept only if it has fewer problems.
  - **Each edit (`fixAd`):** sent with the problem's location three ways: a copy of the ad with a dashed outline around it, with no number since there's one problem per edit (`drawMarkers` in `lib/ads/markers.ts`); the area in words ("from 45% to 89% across and 44% to 81% down"); and what's in it.
  - **Copied markers:** Nano Banana sometimes copies drawn markers into its output (an Apple ad came back with six numbered red circles). The `artifact` check catches them and the next repair removes them. Close-up crops instead of markers were tried and dropped on the user's call, since marking the spot is more precise. Copy problems get no marked image, since an image of the wrong text anchors the model to it. Each edit comes with the real references it needs (the real logo for a `logo` problem, product photos for a product or screen, nothing for a boxed logo, since the logo image's solid background is how the box got there), under retoucher rules: change only inside the box.
  - **Tested on the Gucci bag:** the box sat tightly on the bag and nothing outside it changed. The bag's shape barely moved, so it stayed a remaining problem. Only then is the ad stored, so it stays "being made" until checked, and good ads appear first.
  - **Recorded:** the result is saved as `campaign_ads.verification` ({ checked, first, rounds, fixed, remaining }) and in the tool summary, which the agent relays.
  - **Still wrong after the repairs:** the ad is shown with a warning beside it: an orange ⚠ on its rail thumbnail, and a "Still not right after N fixes" box under its headline listing the problems (`SavedAd.issues`, `AdIssues` in `ad-studio.tsx`). The agent offers a remake.
  - **Steps:** the loop is `runAdFlow` (`lib/ads/flow.ts`, dependency-free), over the phases in `generate.ts`: `startAd` (brief, row, draft), `checkDraft`, `repairDraft`, `finishAd` (store). In the agent each phase, and each repair edit, is its own durable workflow step (`adStart`/`adCheck`/`adRepair`/`adFinish` in `workflow-steps.ts`), so a draft plus three repair rounds (several minutes) never hits one step's 300s limit, and a crash resumes where it was. Drafts and edits live in the bucket as `<campaign>/work-<ad>-0.png` and `work-<ad>-<round>-<edit>.png` until the finish.
  - **Calling the phases:** `runAdFlow` calls them as plain functions, not `phases.check(…)`: as a method call the workflow serializes `this` (the object holding the functions) with the step's arguments and the step fails ("failed to serialize step arguments"). A check or repair step that fails outright is skipped (counted unchecked), not fatal. The prompts also forbid invented products, devices, screens, dashboards or data, and service brands get a `services_note` in the brief: screens may only be the real screenshots. fal's timeout is 150s per image so each phase fits a step.
- **Ad studio and pinned comments** (`components/campaigns/ad-studio.tsx`): sized to the panel with no scrolling. A vertical rail of ads by number on the left (Ad 1 at the top, ads being made at the bottom; newest version, version and open-comment badges), the selected ad as large as fits (`--studio-h` and container units), and its details on the right (ending with "Products in this ad": each product the shown version was made with, from its `product_ids` matched to the catalog, as a photo, name, price and type linking to its page, or "No longer in the catalog"): "Ad N" with a compact version switcher (‹ v2 of 5 ▾ ›: arrows step, the middle opens a scrolling list of every version with what it changed), comments, Apply, Preview (full size in a new tab), Download. Each ad in the rail has a ⋯ menu (top-right of its thumbnail, on hover and always on the selected ad) with Delete Ad, confirmed in a dialog (the UI no longer deletes single versions; the agent's `deleteAd` still can). **Deletes are instant:** the ad (or a comment's pin and list line) shrinks and fades for 0.2s, then leaves the page while the server deletes it in the background; on failure it comes back with an error. The details column scrolls, so it has a little padding to keep card borders and button outlines at its edges from being clipped. Narrow panels stack it. The Ads tab holds only the studio; the headline list is in the Brand kit tab.
- **Edit summaries:** after each edit, `summarizeEdit` (`lib/ads/summarize.ts`, a small vision model, `EDIT_SUMMARY_MODEL`, default Haiku) compares the ad before and after (shrunk to 768px JPEGs) and writes 1–4 short past-tense bullets of what visibly changed, including unrequested changes and leaving out requests that didn't take. They're saved as `campaign_ads.changes`, shown as the version's "Changes" (older versions fall back to their comments, `instruction`), and returned in the `editAd` result; the agent's reply is built from them ("v5 of Ad 2 is ready: I changed the headline to yellow"). Existing edits were backfilled.
- **Comment review:** hovering any pin shows its comment in a card (`Pin` with a HoverCard) with ✓ and ✕ (`CheckOrX`). On an open comment, ✎ turns it into a text box (Enter saves, Escape cancels; the card stays open while editing; saved with `updateAdCommentAction`, restored if that fails), ✓ marks it resolved and ✕ deletes it (both remove it: it shrinks away and is deleted in the background). On an applied one they answer "Was it resolved?" (✓ yes, ✕ no). Each version shows the comments its edit applied (`appliedComments`, via `ad_comments.applied_ad_id`) as yellow "?" pins whose card asks "Was it resolved?". ✓ (yes): the pin shrinks and fades out (0.2s), the comment leaves the page at once, and `reviewAdComment` (`lib/campaigns.ts`) deletes it in the background (on failure it comes back with an error). ✕ (no): it's marked `unresolved` and re-opened at the same spot on the ad's newest version, ready to apply again. Only comments that still need something show as pins: open ones, and applied ones awaiting an answer (yellow on the version the edit made, grey on the version they were pinned on). Answered ones disappear: resolved ones are deleted, and an unresolved one lives on as its reopened copy.
- **Stopping mid-generation:** ad rows record the agent run making them (`run_id`) and fal's request id as soon as it's queued. The stop route (`DELETE …/chat/[runId]`) calls `cancelRunAds` (`lib/ads/render.ts`): it cancels those fal jobs and deletes their rows, so nothing is left loading. A job that finishes anyway is thrown away: `storeAdImage` only completes a row still `generating` whose run is still the campaign's active run (`throwIfStopped`), and an edit checks again before paying for a retry. The page re-reads the ads after a stop. Clicking the newest version pins a numbered comment at that spot (`ad_comments`: x/y as fractions of the image, `open` until applied); **Apply** sends the agent "Apply my comments to the ad … (ad <id>)", and it calls **`editAd`** (`lib/ads/edit.ts`). That sends Nano Banana Pro edit **only the image before the edit** (the base, the single source of truth) and, with pins, a copy with a numbered pin drawn exactly where each comment was placed (`drawMarkers`), with the changes as JSON by comment number and position. After the edit, `findArtifacts` (a marks-only vision check) looks for leftover marks; if any, one combined removal edit runs (if the edit took under 150s, to fit the step) and is kept when it leaves fewer and everything else to keep as in image 1. No product photos or brand lists: given a second picture of the product, the model drifts toward it (a test re-posed the phone). **Edit check** (`lib/ads/retention.ts`, `checkEdit`): the result is compared to the pre-edit image on a 72×128 grid. (1) Did each pinned change happen: at least 5% of the cells near the pin changed (applied edits 54–92%, a no-op 0%). (2) Did the rest stay: the share unchanged outside a radius around the pins, saved as `campaign_ads.retained` (unchanged 100, local edits 92–98, a different ad ~9). A missed pin, an unchanged result, or a pins-only edit under 90% kept gets one retry with a prompt naming what went wrong; the better attempt wins (fewest misses, then most kept). If nothing requested happened, no version is made and the comments stay open; if some pins missed, those comments move to the new version, still open. Edits with an overall instruction aren't retried for drift. The result is a new `campaign_ads` row with `parent_id` (the earlier version stays) and `instruction` (what it changed); applied comments get `applied_ad_id`. The agent can also call `editAd` with an `instruction` from chat ("make the background warmer"). **Brand kit in edits:** by default an edit sends only the ad. `editAd`'s `include` lets the agent add whatever the user's message or pinned comments refer to, and combine them:
  - the real logo (`logo`; inline `data:` SVG logos are decoded too, `logoBytes` in `brand-assets.ts`);
  - chosen colors (`colors`: hex codes or "all", each as text and a swatch image);
  - product photos (`productIds`, including products the ad doesn't show yet);
  - brand visuals (`visuals`: numbers from the V1…Vn list in its instructions);
  - the fonts and voice as text;
  - the user's chat images (`references`).

  The instructions spell out each case ("the logo is wrong" → logo, "add our mascot" → that visual's number). Tested on Anthropic: a pinned "replace the compass with the nautilus from our brand visuals" plus "use our real logo" had the agent send the pinned copy, the decoded SVG logo and V3. The result had the nautilus and the real ANTHROP\C wordmark, but also restyled the headline and background (61% kept). The agent sees the real logo itself: `prepareModelMessages` adds it as an image to the first user message each run. Its instructions list every ad with id, version and open comments. Our images reach fal as 15-minute signed URLs and are recorded by storage path, never by URL.
- **Images in the chat** (references): the input takes up to 4 PNG/JPEG/WebP images per message (attach button, paste or drop; `components/campaigns/chat-attachments.tsx`). On send they're shrunk in the browser (longest side 2048, WebP) and uploaded to the private `chat-uploads` bucket (`POST /api/campaigns/[id]/uploads`, checked by magic bytes, ≤8 MB); the message carries file parts with our own URL (`/api/campaigns/<id>/uploads/<uuid>.<ext>`, signed-in only), never base64. The chat route drops any other file part. Each agent run's `prepareModelMessages` step (`lib/agent/workflow-steps.ts`) swaps those for one-hour signed URLs so the model sees the images (the latest 6; older ones are named only) and adds each one's ref (its file name). `generateAd` and `editAd` take `references: [{ image: <ref>, use: <how> }]`; `resolveReferences` (`lib/uploads.ts`) signs them for fal (15 min) and they go to Nano Banana as extra `image_urls`, described in the prompt and the brief's `user_references`; the ad row records them by storage path. Deleting a campaign deletes its uploads.
- **The agent edits the brand kit** when asked: `editBrandText` (tagline, value proposition, audience/voice descriptions, sample line), `editTags` (audience tags, voice traits), `editColors`, `editFonts`, implemented in `lib/agent/kit-tools.ts` on top of `getEditableKit` / `updateKit`. Each re-reads the kit, changes only what was asked and returns a one-line summary shown in the chat. After a reply that used one, the page refreshes the kit (`router.refresh()`) and drops the panel's local edits, which were already saved.
- **The agent steers research** with the research tools (`lib/agent/research-tools.ts`, schemas in `lib/agent/tools.ts`), one per step in `lib/research/steps.ts`. Steps run as research (they keep edits unless `force`); `setOffering`, `setProductTypes` and `removeProducts` run as the agent, so they count as edits. A tool refuses while a full background run is going, and a missing prerequisite comes back as a message naming the step to run first. The playbook is a skill: `lib/agent/skills/research/SKILL.md` (frontmatter name + description, loaded by `lib/agent/skills.ts`, traced into the chat route by `outputFileTracingIncludes`). The instructions list skills by name and description; the agent loads the body with `readSkill`. Budget: 8 costly research calls per turn (free reads `getCatalog`, `researchStatus`, `listSiteLinks` don't count), enforced with `prepareStep` + `activeTools`; the chat route's `maxDuration` is 300. Research tool calls render as step rows in the chat, and the panel reloads after a turn that used one.
- **Quiet cancels:** the chat transport uses `quietFetch` (`campaign-workspace.tsx`): a stream the page aborts on purpose (leaving, interrupting) just ends, instead of the transport logging "BodyStreamBuffer was aborted". The run itself carries on on the server.
- **Interruptible:** the input stays open while the agent works (a reply or a research run); sending first calls the cancel route (the run stops and saves what it had) and `stop()`, then sends. The chat route drops tool parts an interruption left half-done (`withoutInterruptedParts`) and the agent converts with `ignoreIncompleteToolCalls`. A card the user moved past without continuing is closed as `{ picked: [] }` for the model; its checkboxes keep working.
- A send with fewer messages than the saved thread (a stale tab, a duplicate kickoff) gets a 409 so it can't overwrite newer history.
- Model: `AGENT_MODEL`, falling back to `RESEARCH_MODEL`, then `anthropic/claude-sonnet-5.5`.

## Working agreements

- The user must be able to explain every part of the system in review, so explain the mechanics of what you build and surface product decisions for the user to make rather than deciding silently.
- Do not write the key-decisions note or the architecture diagram; those are the user's own deliverables.
- Session transcripts are a deliverable: keep secrets out of the conversation. Refer to env vars by name, never print their values.
- Secrets live in `.env.local` (gitignored) locally and in Vercel project env vars for deploys.
