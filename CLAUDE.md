# AI Ads

An agentic app that takes an ecommerce marketer from a store URL to 9:16 portrait image ads they would actually run. The example store is https://www.loopycases.com.

## Product loop

URL → **Research** (brand + products) → **Generate** (image ads) → **Manage** (review, iterate, approve) → feedback back into Generate. The agent does the work; the user steers.

- **Onboard:** research the brand (logo, colors, voice, value prop, audience) and pull real product images and details from the store. Decide deliberately what is scraped, what is inferred, and what is asked of the user.
- **Generate:** full-screen 9:16 portrait ads built on the store's **real product photos**, never an invented product, with the headline and CTA rendered inside the image.
- **Manage:** brand kit, campaigns, ads, variants, assets and status persist in Supabase. The user can give feedback, edit, regenerate and approve.
- **Human in the loop:** at least one point where the agent pauses for user input, and one where user feedback changes the next generation.

Working software that feels good beats breadth. Tool failures must degrade gracefully, never dead-end.

## Stack (fixed by the brief — do not swap layers)

- Next.js 16 App Router, React 19, Tailwind 4, TypeScript
- Vercel AI SDK + AI Elements for the agent and chat UI (streaming, tool calls, generative UI); **Vercel Workflow** (`workflow`, `@ai-sdk/workflow` `WorkflowAgent`) runs the agent durably
- Supabase: Postgres, Storage, optional Auth (a single demo user is fine)
- fal.ai for image generation. fal URLs are not durable: **always copy outputs into Supabase Storage** and store our URL, never fal's.
- Firecrawl or a web search API for research
- LLM via Vercel AI Gateway
- Hosted on Vercel, project `jiu-jiu-s-team/ai-ads`, connected to GitHub `jooj99/ai-ads`. Pushes to `main` deploy to production at https://ai-ads-dusky.vercel.app; PRs get preview deploys.

## Check current docs, not memory

Next.js 16, the AI SDK and AI Elements change faster than model training data. Before writing framework code, read the version-matched docs instead of relying on recall:

- Next.js: `node_modules/next/dist/docs/` (matches the installed version). Heed deprecation notices.
- `cacheComponents` and `partialPrefetching` are enabled in `next.config.ts`, so caching follows the Cache Components model (`"use cache"`, `cacheLife`, `cacheTag`), not older `fetch`/`unstable_cache` patterns.
- AI SDK, AI Elements, Supabase and fal: check their current docs or the installed packages' types before using an API.

## Auth (one demo user)

- **Supabase Auth, email + password, one user.** `@supabase/ssr` keeps the session in cookies. The auth client (`lib/supabase/auth.ts`) uses the publishable key, so it can sign in but still can't read tables; data stays on the secret-key client. Auth only decides who may use the app, so tables have no `user_id` and RLS stays policy-free.
- `proxy.ts` runs on every page and API request: it refreshes the session (`getClaims()` verifies the JWT) and sends signed-out visitors to `/login?next=<path>` (pages) or a 401 (API). It skips Next's assets, images in `public/`, and `/.well-known/workflow/*` (the Workflow runtime calls those server-to-server, with its own queue key). Without the public Supabase env vars it fails closed.
- Checks don't rely on the proxy alone: every route handler starts with `unauthorized()`, every server action and data-loading page with `requireUser()`.
- `/login` (`app/login/`): `signIn` / `signOut` server actions; `next` only accepts same-site paths. Sign out is in the sidebar's account menu.
- The demo user is created with `npm run demo-user` (`scripts/create-demo-user.mjs`, admin API, already confirmed; rerun to reset the password) from `DEMO_USER_EMAIL` / `DEMO_USER_PASSWORD` in `.env.local`. There's no sign-up page; public sign-ups should also be off in the Supabase dashboard (Authentication → Sign In / Providers → "Allow new users to sign up"), since the publishable key could otherwise register accounts through the API.

## Campaigns and brand research

- Home's **Start Campaign** (`app/actions.ts` server action) validates the URL, inserts a `campaigns` row, claims it (`claim_research` SQL function: one run at a time, a run quiet for 5 min counts as dead), starts the durable research run (`start(researchRun, [id])`), records it as the campaign's active run with its opening message (`openResearchThread`, `lib/agent/research-thread.ts`) and redirects to `/campaigns/[id]`. `POST /api/campaigns/[id]/research` starts a run the same way (from the empty-chat card's Start / Restart research, or the agent's full re-run) and returns the run id and opening message.
- Research runs **independent of any page**: it's a durable Vercel Workflow run (see the agent section), so leaving the page, function timeouts and restarts don't stop it, and the page reconnects to its stream. **Supabase Realtime** (`lib/realtime.ts`) still carries headline changes (status, name, logo, current step) on `campaigns` for the live Campaigns grid, and a `finished` event on `campaign:<id>`. Broadcasts are sent with the secret key and received with the publishable key; tables stay locked behind RLS.
- Without `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (Vercel only syncs them to Production; locally they're in `.env.development.local`) pages fall back to polling.
- Supabase schema: `supabase/migrations/` (`campaigns`, `brand_kits` 1:1, `campaign_products`, `campaign_chats` 1:1, `campaign_headlines`, `campaign_ads` (versions via `parent_id`), `ad_comments`; private Storage buckets `brand-fonts` and `ads`). RLS is on with no policies; all access goes through `lib/supabase/server.ts` with the secret key, and `lib/campaigns.ts` is the only data layer. Apply migrations with `npx supabase@2 db push --db-url "$POSTGRES_URL_NON_POOLING"`.
- `campaign_products` holds the **whole** researched catalog, each row typed (`type_name`) with heroes flagged (`is_hero`); the Product selection filters All / Hero picks / each type.
- Editing: click the campaign title to rename; delete from the campaign page or list card; remove colors/fonts from the brand kit. All go through server actions in `app/campaigns/actions.ts`. Research only renames a campaign while its name is still the default (the domain).
- What the research steps do: Shopify detection (`/meta.json`) and the homepage read (Firecrawl full page incl. navbar and footer: `markdown` + `branding` + `links` + `rawHtml`); a quick Haiku call (`lib/research/offering.ts`) classifies the business as **goods or services**; the catalog follows from that (`lib/research/catalog.ts`): goods use Shopify `/products.json` or one product page per navbar category, services use the site's service pages and their own photos (never the Shopify retail shop). Then two `streamText` + `Output.object` calls (`lib/research/insights.ts`) write value prop, audience and voice, and group the **whole** catalog into at most 10 kinds of product/service (styles and collections are not types) with 1–2 hero picks each. Picks without photos get their pages read afterwards (plain HTML first, to spare Firecrawl's ~15 req/min free limit).
- **Research is built from steps** (`lib/research/steps.ts`): `detectPlatform`, `readSite`, `classifyOffering` / `setOffering`, `listSiteLinks`, `findOfferingPages`, `loadCatalog`, `removeProducts`, `writeBrandInsights`, `groupCatalog` / `setProductTypes`, `findPhotos`, plus the read-only `getCatalog` and `researchStatus`. Each reads what earlier steps stored, does one job, saves, and returns a one-line summary; a missing input throws `StepPrerequisiteError` naming the step to run first. The agent runs them itself as tools, following the research skill (usual order: platform ∥ homepage → offering → catalog → brand insights ∥ grouping → photos). The insights call is split in two (`streamBrandInsights`, `streamCatalogGrouping`, both taking optional `guidance`); the Haiku calls take `guidance` too. Each session saves only the kit columns it changed, so steps running in parallel don't overwrite each other.
- **Research state** (`lib/research/state.ts`, `ResearchSession`): `research_snapshots` keeps what steps read (page reads by URL, the Shopify detection, the link picks). Products merge by `source_id` (unique per campaign) and keep `listed_type`, `tags` and `origin`; a "replace" re-run only drops research-added items, and a full re-read is the truth about photos. Fields the user or agent edit are listed in `brand_kits.edited` (via `updateKit`'s `fields`) and research never overwrites them unless the session is opened with `force`. After page-based loads the shared-photo rule (`sharedPhotoCleanup`) runs over the whole merged catalog, photos are applied per item id, and photo searches skip pages that describe several items (the homepage, a pricing page); videos and YouTube thumbnails are never photos. Merges match items by id or by page URL (host without www, path), so the same product found as a Shopify id and as a page isn't duplicated; items titled like error pages ("404 Not Found") are dropped. `loadCatalog` with `mode: "add"` requested in chat runs as the agent, so those items are marked `origin = agent` and survive research re-runs.
- When Firecrawl's `branding` leaves gaps (no real logo, under two colors, missing or internal font names), `lib/research/html-signals.ts` reads the rendered HTML plus up to four stylesheets: logos from structured data, `<img>`, CSS `mask`/`background` images (scored by home link, aria-label and selector so header icons lose) and inline SVG; colors from CSS design tokens; readable font names from `@font-face` files. If there's still no logo, `probeLogoPaths` checks `/logo.svg`, `/assets/logo.png` and similar.
- **Brand font files:** research always reads the site's stylesheets (`fetchStylesheets`, keeping each sheet's URL so relative `url()`s resolve) and `fontFilesFor` attaches each brand font's own `@font-face` files (regular ≈400 and bold ≈700, upright, WOFF2 first, the subset whose `unicode-range` covers "A"; names matched loosely and through internal aliases). After the run, `storeFontFiles` (`lib/research/font-store.ts`) copies them into the private `brand-fonts` bucket (checked by magic bytes, ≤2 MB, named by content hash) and the kit stores `/api/campaigns/<id>/fonts/<file>`, which streams them back same-origin with immutable caching. The font preview loads those with the FontFace API, then tries Google Fonts, then says it's a fallback. Deleting a campaign deletes its font files. Licensed fonts stay private to the campaign.
- Images: don't use Firecrawl's `images` format. It splits srcsets on commas inside image-CDN URLs (`static.nike.com/a/images/c_limit,w_318,…`), producing dead fragments. Request `rawHtml` and use `imagesFromHtml` (srcset-aware, reads `<picture><source>`, drops fragments via `isImageFragment`). A photo shared by two or more items, the homepage's share image and the logo are never an item's photo and are dropped (`withoutSiteChrome`, `notItemPhotos`, `pickPhotoExclusions`); self-described banners rank last (`DECORATION`). Items with no photo of their own (plans, integrations) show a typographic tile instead of a borrowed picture.
- Scraped facts (logo, colors, fonts, products, images) never pass through the model; it only returns product ids, which are matched back to the real catalog.
- Needs `FIRECRAWL_API_KEY` and AI Gateway access (OIDC via `vercel env pull`, or `AI_GATEWAY_API_KEY`). Without them each step degrades and says so instead of failing.
- Model: `anthropic/claude-sonnet-5.5` by default (needs paid Gateway credits); override with `RESEARCH_MODEL`. The local OIDC token expires after ~12h; rerun `vercel env pull .env.local` if the Gateway starts rejecting requests.

## Campaign workspace and agent chat

- `/campaigns/[id]` (`components/campaigns/campaign-workspace.tsx`): the panel (ads, brand kit, products) on the left and the agent chat on the right (`campaign-chat.tsx`; phones stack them, chat first), the Brand kit / Products / Ads tab buttons in the header (the `Tabs` root wraps the page; their content fills the right panel), and Delete in the ⋯ menu. **The ads are the main view:** the page opens on Ads once there are any and switches to it when the agent starts making or editing one. The chat input starts as one line and grows with the message.
- The research run appears in the thread as the agent's first turn (`research-progress.tsx`), still driven by the Realtime broadcasts above; it is not an LLM message.
- **The agent is durable** (`workflows/agent.ts`): `researchRun(campaignId)` (Start Campaign / Research again: the agent follows the research skill, then proposes headlines) and `agentTurn(campaignId, messages)` (one chat turn) are Vercel Workflow runs of a `WorkflowAgent`. Its instructions are built in a step (`loadAgentSetup`); every server tool call is its own retried step (`executeServerTool` → `lib/agent/server-tools.ts`, which also keeps a research run's heartbeat and the grid's step label fresh); the reply is rebuilt from the run's stream and saved by `saveRunThread` (seeded with the last assistant message when a submitted card continues it; skipped if a newer run took over). `campaigns.agent_run_id` is the active run. Routes: `POST /api/campaigns/[id]/chat` validates, saves the thread and starts `agentTurn` (header `x-workflow-run-id`); `GET …/chat/[runId]/stream` replays and follows a run (`[runId]` = the campaign id means its active run); `DELETE …/chat/[runId]` interrupts via the run's cancel hook (soft: the reply so far is saved), with `run.cancel()` as a backstop. The client uses `WorkflowChatTransport` and `useChat({ resume })` when the page loads with an active run. `instrumentation.ts` starts the Workflow world so dev-server restarts resume runs. Steps re-run from the start after a crash, so they must stay idempotent (upserts by id).
- Brand kit panel: colors and fonts share a row; audience is tags (remove ✕ revealed on hover, add your own), saved with the same server action as color/font removals. Research still writes an audience description, but only the agent sees it. Hovering a font previews it (see brand font files below). Sections the user or agent edited show an **Edited** badge (from `brand_kits.edited`, plus panel edits optimistically); a hand-set grouping shows "grouping edited"; products the agent or user added show "Added by agent" / "Added by you". A chat with no messages yet (campaigns researched before research became the agent's run, or dead runs) shows `ChatStart` with the next action: start or restart research, or "Get headline ideas".
- **Human in the loop:** the research run ends by calling `proposeHeadlines`, a tool with no `execute`, so the run ends with a choice card (`headline-choice.tsx`) waiting; the card's answer starts the next `agentTurn`.
- **Headlines are a list** in `campaign_headlines` (unique per campaign + headline + CTA, `source` agent/user, `proposal_id` = the card's tool call). On a card, ticking options and "Write your own" only change a local selection; **Submit** saves the changes (server actions in `app/campaigns/actions.ts`) and sends them to the agent: as the `proposeHeadlines` tool output (`{ picked, removed }`, auto-sent by `sendAutomaticallyWhen`) when the agent is waiting on that card, or as a chat message ("Headlines from an earlier set: …") for an older card. Any card can be changed and resubmitted. The agent's instructions list the saved headlines every turn, with the ones just submitted listed apart so it doesn't read them as duplicates. The agent can also change them in chat with the server tools `saveHeadline` / `removeHeadline`; the client re-reads the list when a reply finishes. The Brand kit tab lists them below the kit (`HeadlinesCard`) with remove and write-your-own (saved directly).
- **Generate (ads):** the agent's `generateAd` tool (`lib/agent/tools.ts`, run by `lib/ads/generate.ts`) makes one full-screen 9:16 ad per call with **Nano Banana Pro edit** on fal (`fal-ai/nano-banana-pro/edit`, `aspect_ratio: "9:16"`, 2K PNG, key `FALAI_KEY`). When the user submits headlines (the card's `picked`, or an older card's message), the instructions have the agent call it once per new headline, in parallel, choosing 1–2 hero products by catalog id for each (default: the first hero with a photo). `lib/ads/brief.ts` turns the kit into the model input: the products' real photos (only ones that load, checked first), the **real logo** and a **solid swatch image per brand color** (`lib/ads/brand-assets.ts`: the logo is fetched, rendered to PNG if it's an SVG, stored as `<campaign>/logo-<hash>.png`; swatches are 256px squares at `<campaign>/swatch-<HEX>.png`; both go to fal as 15-minute signed URLs), as `image_urls` (14 at most); standing rules (real products only, exact copy, safe zones) at the top of the prompt, since fal's documented input for this endpoint has no system field (stored separately in `campaign_ads.system_prompt` for review); and the ad's brief as **JSON** in `prompt` (headline, CTA, hero products by image number, each color as hex + role + the job it does from its role, e.g. Primary → the CTA button, + its swatch image, fonts with roles, voice traits and description, audience). The rules say to reproduce the logo exactly and use swatch colors exactly. Tested on Reconero: the CTA came out at the brand primary; the logo is shaped by the real one but still approximated on new ads, while an edit with `include.logo` reproduced it exactly. The image is copied from fal into the private `ads` bucket and served signed-in only at `/api/campaigns/<id>/ads/<file>`; `campaign_ads` keeps each ad's status (generating/ready/failed), inputs and prompt. A retried workflow step finds its finished ad by `tool_call_id` instead of paying again. At most 6 ads per chat turn (`prepareStep`). The chat shows each call as a spinner, then a thumbnail. The model returns 1536×2752 PNGs.
- **Ad numbers:** every ad has a number per campaign (`campaign_ads.number`, "Ad 3"), assigned by a database trigger from `campaigns.ad_counter` (never reused, even after deletes); every version of an ad shares it, so an ad is all rows with one number. The agent's instructions list ads by number with each version's id, and it refers to them by number. `deleteAd` (agent tool and the studio's buttons, both via `lib/campaigns.ts`) deletes one version or the whole ad, images included.
- **Ad studio and pinned comments** (`components/campaigns/ad-studio.tsx`): sized to the panel with no scrolling. A vertical rail of ads by number on the left (Ad 1 at the top, ads being made at the bottom; newest version, version and open-comment badges), the selected ad as large as fits (`--studio-h` and container units), and its details on the right: "Ad N" with a compact version switcher (‹ v2 of 5 ▾ ›: arrows step, the middle opens a scrolling list of every version with what it changed), comments, Apply, Preview (full size in a new tab), Download. Each ad in the rail has a ⋯ menu (top-right of its thumbnail, on hover and always on the selected ad) with Delete Ad, confirmed in a dialog (the UI no longer deletes single versions; the agent's `deleteAd` still can). **Deletes are instant:** the ad (or a comment's pin and list line) shrinks and fades for 0.2s, then leaves the page while the server deletes it in the background; on failure it comes back with an error. The details column scrolls, so it has a little padding to keep card borders and button outlines at its edges from being clipped. Narrow panels stack it. The Ads tab holds only the studio; the headline list is in the Brand kit tab.
- **Edit summaries:** after each edit, `summarizeEdit` (`lib/ads/summarize.ts`, a small vision model, `EDIT_SUMMARY_MODEL`, default Haiku) compares the ad before and after (shrunk to 768px JPEGs) and writes 1–4 short past-tense bullets of what visibly changed, including unrequested changes and leaving out requests that didn't take. They're saved as `campaign_ads.changes`, shown as the version's "Changes" (older versions fall back to their comments, `instruction`), and returned in the `editAd` result; the agent's reply is built from them ("v5 of Ad 2 is ready: I changed the headline to yellow"). Existing edits were backfilled.
- **Comment review:** hovering any pin shows its comment in a card (`Pin` with a HoverCard) with ✓ and ✕ (`CheckOrX`). On an open comment, ✓ marks it resolved and ✕ deletes it (both remove it: it shrinks away and is deleted in the background). On an applied one they answer "Was it resolved?" (✓ yes, ✕ no). Each version shows the comments its edit applied (`appliedComments`, via `ad_comments.applied_ad_id`) as yellow "?" pins whose card asks "Was it resolved?". ✓ (yes): the pin shrinks and fades out (0.2s), the comment leaves the page at once, and `reviewAdComment` (`lib/campaigns.ts`) deletes it in the background (on failure it comes back with an error). ✕ (no): it's marked `unresolved` and re-opened at the same spot on the ad's newest version, ready to apply again. Pins on the version a comment was made on stay grey with where it was applied.
- **Stopping mid-generation:** ad rows record the agent run making them (`run_id`) and fal's request id as soon as it's queued. The stop route (`DELETE …/chat/[runId]`) calls `cancelRunAds` (`lib/ads/render.ts`): it cancels those fal jobs and deletes their rows, so nothing is left loading. A job that finishes anyway is thrown away: `storeAdImage` only completes a row still `generating` whose run is still the campaign's active run (`throwIfStopped`), and an edit checks again before paying for a retry. The page re-reads the ads after a stop. Clicking the newest version pins a numbered comment at that spot (`ad_comments`: x/y as fractions of the image, `open` until applied); **Apply** sends the agent "Apply my comments to the ad … (ad <id>)", and it calls **`editAd`** (`lib/ads/edit.ts`). That sends Nano Banana Pro edit **only the image before the edit** (the base, the single source of truth) and, with pins, a copy with the numbered pins drawn on it (`lib/ads/markers.ts`, sharp; a guide the model is told never to draw), with the changes as JSON by pin number and position and everything else to keep as in image 1. No product photos or brand lists: given a second picture of the product, the model drifts toward it (a test re-posed the phone). **Edit check** (`lib/ads/retention.ts`, `checkEdit`): the result is compared to the pre-edit image on a 72×128 grid. (1) Did each pinned change happen: at least 5% of the cells near the pin changed (applied edits 54–92%, a no-op 0%). (2) Did the rest stay: the share unchanged outside a radius around the pins, saved as `campaign_ads.retained` (unchanged 100, local edits 92–98, a different ad ~9). A missed pin, an unchanged result, or a pins-only edit under 90% kept gets one retry with a prompt naming what went wrong; the better attempt wins (fewest misses, then most kept). If nothing requested happened, no version is made and the comments stay open; if some pins missed, those comments move to the new version, still open. Edits with an overall instruction aren't retried for drift. The result is a new `campaign_ads` row with `parent_id` (the earlier version stays) and `instruction` (what it changed); applied comments get `applied_ad_id`. The agent can also call `editAd` with an `instruction` from chat ("make the background warmer"). **Brand kit in edits:** by default an edit sends only the ad; `editAd`'s `include` lets the agent add the real logo (`logo`), chosen colors (`colors`: hex codes or "all", each as text and a swatch image), product photos (`productIds`), and the fonts and voice as text, as the change needs ("use the real logo" → `include.logo`). The agent sees the real logo itself: `prepareModelMessages` adds it as an image to the first user message each run. Its instructions list every ad with id, version and open comments. Our images reach fal as 15-minute signed URLs and are recorded by storage path, never by URL.
- **Images in the chat** (references): the input takes up to 4 PNG/JPEG/WebP images per message (attach button, paste or drop; `components/campaigns/chat-attachments.tsx`). On send they're shrunk in the browser (longest side 2048, WebP) and uploaded to the private `chat-uploads` bucket (`POST /api/campaigns/[id]/uploads`, checked by magic bytes, ≤8 MB); the message carries file parts with our own URL (`/api/campaigns/<id>/uploads/<uuid>.<ext>`, signed-in only), never base64. The chat route drops any other file part. Each agent run's `prepareModelMessages` step (`lib/agent/workflow-steps.ts`) swaps those for one-hour signed URLs so the model sees the images (the latest 6; older ones are named only) and adds each one's ref (its file name). `generateAd` and `editAd` take `references: [{ image: <ref>, use: <how> }]`; `resolveReferences` (`lib/uploads.ts`) signs them for fal (15 min) and they go to Nano Banana as extra `image_urls`, described in the prompt and the brief's `user_references`; the ad row records them by storage path. Deleting a campaign deletes its uploads.
- **The agent edits the brand kit** when asked: `editBrandText` (tagline, value proposition, audience/voice descriptions, sample line), `editTags` (audience tags, voice traits), `editColors`, `editFonts`, implemented in `lib/agent/kit-tools.ts` on top of `getEditableKit` / `updateKit`. Each re-reads the kit, changes only what was asked and returns a one-line summary shown in the chat. After a reply that used one, the page refreshes the kit (`router.refresh()`) and drops the panel's local edits, which were already saved.
- **The agent steers research** with the research tools (`lib/agent/research-tools.ts`, schemas in `lib/agent/tools.ts`), one per step in `lib/research/steps.ts`. Steps run as research (they keep edits unless `force`); `setOffering`, `setProductTypes` and `removeProducts` run as the agent, so they count as edits. A tool refuses while a full background run is going, and a missing prerequisite comes back as a message naming the step to run first. The playbook is a skill: `lib/agent/skills/research/SKILL.md` (frontmatter name + description, loaded by `lib/agent/skills.ts`, traced into the chat route by `outputFileTracingIncludes`). The instructions list skills by name and description; the agent loads the body with `readSkill`. Budget: 8 costly research calls per turn (free reads `getCatalog`, `researchStatus`, `listSiteLinks` don't count), enforced with `prepareStep` + `activeTools`; the chat route's `maxDuration` is 300. Research tool calls render as step rows in the chat, and the panel reloads after a turn that used one.
- **Interruptible:** the input stays open while the agent works (a reply or a research run); sending first calls the cancel route (the run stops and saves what it had) and `stop()`, then sends. The chat route drops tool parts an interruption left half-done (`withoutInterruptedParts`) and the agent converts with `ignoreIncompleteToolCalls`. A card the user moved past without continuing is closed as `{ picked: [] }` for the model; its checkboxes keep working.
- A send with fewer messages than the saved thread (a stale tab, a duplicate kickoff) gets a 409 so it can't overwrite newer history.
- Model: `AGENT_MODEL`, falling back to `RESEARCH_MODEL`, then `anthropic/claude-sonnet-5.5`.

## Working agreements

- The user must be able to explain every part of the system in review, so explain the mechanics of what you build and surface product decisions for the user to make rather than deciding silently.
- Do not write the key-decisions note or the architecture diagram; those are the user's own deliverables.
- Session transcripts are a deliverable: keep secrets out of the conversation. Refer to env vars by name, never print their values.
- Secrets live in `.env.local` (gitignored) locally and in Vercel project env vars for deploys.
